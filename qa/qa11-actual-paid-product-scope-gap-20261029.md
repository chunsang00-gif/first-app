# QA11 실제 유료 상품 범위: 12장·35항목 약속과 코드의 차이

검토일: 2026-10-29. **실제 첫 유료 요청의 생성 직전 prompt 및 실제 JSON Schema 경계**와 동일한 코드에서 무료 테스트로 확인했다. 모델 응답이나 독자의 삶을 생성하거나 판정한 것이 아니다.

## 확정된 계약 불일치

- 품질 검증의 12개 canonical chapter ID와 `report-outline.js`의 12개 장 정의는 일치한다.
- 하지만 `report-outline.topics`의 전체 세부 질문은 **28개**다. 목표 **35개보다 7개 적다**.
- `report-wire.schemaFor`는 이 28개 정의를 해당 장의 원고 필드명으로 사용하고, 필수 근거(anchor) 외 문단에는 **null**이 허용될 수 있다. 코어 첫 장도 QA 전용 추가 슬롯을 켠 경우가 아니면 공식적으로 `temperament`와 `strength` **2개**뿐이다.
- 실제 생성 함수는 `report-chapter-selection.select()`를 사용해 독립된 명리 근거가 없는 장을 유료 호출 전에 생략할 수 있다. 이 방식은 근거 없는 해석을 만들지 않기 위한 안전 장치다. 따라서 **12장은 고정 출력이 아니고**, 28개 세부 질문도 고정 출력이 아니다.
- 과거 `report-wire.js`에 남아 있던 '35 topics structural requirements' 주석은 실제 구현과 달라 수정했다. 이용자에게 '35항목이 검증됐다'고 주장해서는 안 된다.

## 두 합성 명식의 실제 계획

| 무료 계산 입력 | 생성 계획 장 수 | 선택된 장의 정의된 질문 최대치 | 독립 근거상 작성 가능 질문 상한 | 본문+종합 모델 호출 계획 |
|---|---:|---:|---:|---:|
| 음력 1982-11-24 오후 2:20, ISFP | **9장** | **22개** | **19개** | **7회** |
| 양력 1994-07-15 오후 2:20, ISFP | **10장** | **24개** | **19개** | **7회** |

이 숫자는 **모델을 호출하기 전에 계산한 상한**이다. 실제 작성·표시·품질 검증된 문단 수가 아니다. 비필수 항목은 모델이 null을 반환할 수 있다. '19개'는 문단 19개를 확보했다는 뜻도, 19개의 유료 고객 가치가 있다는 뜻도 아니다.

## 수행한 실제 검증

- `report-qa11-premium-scope-audit.js`: `report-quality-node.IDS` + `report-outline.topics` + `report-analysis-guidance.preflight` + `report-chapter-selection` + `report-paid-batch-plan`과 실제 제공되는 첫 유료 `report-wire.schemaFor`를 직접 대조한다. 출시 관련 반환값은 `canPromise12Chapters35Topics=false`, `canSell=false`로 유지한다.
- `report-qa11-premium-scope-audit-tests.js`: 위 두 입력을 `report-core-paid-full-prompt-capture.capture()`로 실제 첫 유료 요청 **직전에 인터셉트**한다. 제공자 호출 없음. 일치하지 않는 요청 장 구성·출처 JSON 구조는 실패.
- `package.json`에 전체 `npm test` 등록. 기존 원고·provider API·decoder·원국 계산 알고리즘·배포 설정은 수정하지 않는다.
- CI `40824073770`: `npm test` 및 `npm run smoke` 모두 **SUCCESS**. 구현 커밋 `e374eaa3b5804e249158d483a0ba739d4f5dcfe5`와 연결. OpenAI API 실제 호출 0회.
- `main`과 `saju-mbti-app`는 변경하지 않았다.

## 유료화의 근본 장애와 안전한 수정 순서

1. **상품 규격을 먼저 일치시켜야 한다.** 실제로 모든 사람에게 근거가 있는 35개 독립 질문을 제공할 수 있는지, 또는 **'근거에 따라 달라지는 심화 분석'**이라고 표기할지 정해야 한다. 현재 구현에서 '12장·35항목 고정 제공'이라고 광고하면 틀릴 수 있다.
2. 단순히 `report-outline`에 세부 질문 7개를 복제해 추가하면 28개에서 35개로만 숫자가 늘고, 근거 매핑·쓰기 작업·검증·중복 제거·JSON 계약이 일치하지 않아 품질/결제 실패 위험이 커진다. **임의로 7개를 추가하지 않는다.**
3. 다음 실무 작업에서 12개 장 각각의 **실제 근거·작성 가능/생략 사유**와 목표 35항목의 원래 제품 의미를 매핑해, 어떤 주제를 진짜 독립적으로 보강할 수 있는지 정한다. 그 후 소규모 단위로 서버 근거→문단 출력→검증을 연동한다.
4. 상품 규격이 맞더라도 이는 기술 구조의 문제만 해결한 것. 기존 한 번 실패한 유료 QA5의 원인(필수 연구 문단 null/근거 누락), 실제 제공자 모델의 응답 성공률, 명리 전문 심사와 자연스러운 유료 원고의 독자 가치가 아직 남는다.
5. 새 모델 유료 호출은 **새로운 명시적 사용자 승인** 전 금지. 과거 QA5 승인 재사용·운영 배포·결제 실험 금지.

결론: 기술적 12장 정의는 존재하지만, **검증된 고정 12장·35항목 상품은 현재 없다.** 추가 문장 테스트가 아니라 상품 규격과 실제 생성/출처 계약을 맞추는 일이 최우선.
