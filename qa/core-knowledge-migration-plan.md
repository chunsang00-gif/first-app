# 오프라인 명리 해석 데이터베이스 — 1차 수직 검증

목표: 기존 `report-facts-node.js`의 검증된 사주 계산 결과를 이용해 AI 호출 없이 첫 챕터를 구성한다.

## 구현 범위
- `report-core-knowledge.json`: 십성 10개의 해석 범위와 **편인(월간) → 편재(월지 본기)** 2개 실제 출생 사례에 맞춘 장면/장점/빠뜨리기 쉬운 조건을 기록한 **검토 후보 데이터**.
- `report-core-knowledge-engine.js`: 실제 계산값·출생 위치·본기/월간의 일치 여부를 확인하고 알맞은 DB 규칙만 선택한다.
- 출생월 지지·계절 구분·겉글자와 본기의 오행 관계를 모두 검사한다. 같은 두 십성이라도 맥락이 다른 사주에는 미검토 글을 복사하지 않는다. 같은 분류가 두 위치에 있어도 다른 성격 두 개나 강도 두 배를 꾸미지 않는다. 두 분류를 임의로 섞지 않는다. 저장된 규칙이 없는 조합은 `not-covered`로 종료한다.
- 독자용 문장과 내부 계산 근거를 분리한다. MBTI, 2027 운세, 실제 행동·강약·사건은 추정하지 않는다.
- 항상 `draft-for-human-review`, `releaseVerdict: not-approved`, `apiCalls: 0`.
- **유료 보고서 서비스에 연결하거나 배포하지 않았다.** 기존 사용자 입력, 결제, 계산, AI 보고서 코드는 그대로 유지한다.

## 다음 단계의 통과 기준
1. 전문가 또는 사람의 실제 원문 교정으로 첫 규칙의 명리 타당성·자연스러운 한국어·생활 장면을 승인.
2. 서로 다른 실제 출생 계산값에서 조합·순서·계절의 근거가 달라질 때 다른 결론이 필요하면 조건별 규칙 추가. 뒷받침 없이 일반론 작성 금지.
3. 첫 챕터의 검증된 조합을 단계적으로 확대하고 예상 입력의 빈도를 점검해 커버리지 측정.
4. 기존 모델 기반 유료 생성과 명확히 분리한 시범 기능/플래그를 만들고 회귀 테스트 뒤 운영 적용 여부 판단.

**주의:** `npm test` 통과는 앱 내 원고 품질 합격이나 유료 출시 승인을 뜻하지 않는다.

## v0.2 추가 검증
- 첫 사례: 1982년 음력 11월 24일, 월간 편인·월지 본기 편재, 丑월 전환월, 두 출처 간 오행 관계 확인.
- 둘째 사례: 1994년 양력 4월 15일, 辰월에서 같은 정인 분류 2회. 하나의 해석 관점으로만 설명.
- 출력은 모두 검토 후보이며 유료 앱에서는 사용하지 않는다. DB에 없는 맥락은 `not-covered`.
- **현재 DB는 2개의 맥락별 해석 규칙만 보유한다. 전문 사주 데이터베이스가 완성된 상태가 아니다.**

## v0.3 - 출생 사주 전체의 독립 검증 근거

- `report-core-evidence-graph.js`에서 **연·월·시의 겉글자**, **일간과 같은 오행이 나타난 출생 자리**, **출생 자리끼리 실제 계산되는 관계**를 원본 사주로 다시 계산해 검증한다. 시주를 모르면 해당 근거는 사용하지 않는다.
- `report-core-knowledge.json`에 첫 번째 별도 출처 규칙 1개를 추가: 태어난 **해 겉글자의 정인**과 **달 겉글자의 편인**이 실제로 확인되고, 양쪽이 같은 오행 분류군에 속하면서 종류가 다를 때만 별도의 검토용 문단을 만든다. 기존 월간·본기의 편인/편재 규칙과 명확히 구별한다.
- 동일한 명리 분류를 여러 위치에서 봐도 **성격이 두 개**, **기운이 강해짐**, **충으로 뿌리가 소멸** 등의 주장을 추가하지 않는다. 출생 자리 사이의 충·형 등은 표의 일치 사실만 내부 자료로 보관한다.
- 사주 전체의 근거표는 검토용 `wholeChartEvidence`로 반환하지만, 승인되지 않은 뿌리·충·연운 해석을 고객 문장에 자동 삽입하지 않는다.
- 기존 독자용 첫 문단 1개에서, 외부 출처가 확인될 때만 독립적인 문단 하나를 추가한다. 두 번째 실제 사주와 미지원 조합은 임의로 이 문단을 재사용하지 않는다.
- **현재 범위:** 출생월 규칙 2개 + 위치 간 비교 규칙 1개. 완성된 고급 명리 DB나 판매 승인은 아님.

### 이후 품질 검토에서 필요한 것

- 출생월과 연·시의 역할 차이에 대한 명리 전문가의 검토.
- 기존의 단순 장비/교통 상황 예시가 실제 유료 풀이에 적합한지 교정.
- 각 규칙별 채택률·근거 수·독자 문장 품질 측정.
- 앱의 기존 유료 생성 흐름에는 연결하지 않으며 전환 여부는 사람의 검토 이후 별도 결정.

## v0.4 - 잘못된 DB 조건 차단 + 실제 출생일 테스트

- 십성 이름이 형식상 존재하는 것만으로는 규칙을 승인하지 않는다. **실제 월지 본기·일간·겉글자를 구성했을 때 해당 십성 조합과 오행 방향, 계절 분류가 동시에 성립하는지** 모든 10천간 후보로 검증한다.
- 서로 다른 출생 위치를 비교하는 규칙도 실제 같은 오행 계열이면서 세부 분류가 서로 다른지 재검증한다. 성립 불가능한 DB 수정은 자동 테스트에서 차단된다.
- `report-core-knowledge-coverage.js`는 8개 출생연도×12개월의 고정 양력 검증 그리드와 기존 검증용 사주 변형 3개, 총 **99건**에 대해 자동으로 적용률·미지원 조건·동일 원고 재사용을 계산한다. 이는 실사용자 분포가 아니라 재현 가능한 개발용 표본이다.
- **해석문 중복 감지**: 출생 사주 네 기둥이 다른데도 독자용 원고가 글자 그대로 같으면 별도 집계한다. 다른 출생 시각이 항상 다른 풀이를 요구한다는 뜻은 아니며, DB 규칙이 어떤 정보를 쓰지 않는지 식별하기 위한 점검이다.
- 통계가 아무리 좋아도 원고는 `draft-for-human-review`이고 `not-approved`이다. 기준 없이 모든 사용자에게 채워 넣는 범용 문장은 만들지 않는다.
- DB 커버리지를 넓히려면 실제 사례를 기반으로 **원문 품질 검토를 거친 해석 조건**을 추가해야 하며, 원고 차별화를 목적으로 근거 없는 개성이나 장단점을 생성하면 안 된다.

## v0.5 - 조건별 해석을 조립할 수 있는 감사 가능한 근거 계획

- `report-core-composition.js`: 기존 실제 사주 근거표에서 **월간과 월지 본기 2개 → 연간/시간 실제 출처 → 월지가 직접 관련된 출생 지지 관계 → 일간과 같은 오행이 나타난 위치** 순서로 검토용 근거 계획을 구성한다.
- 십성 10개 기본 의미와 **각 출생 위치의 실제 계산된 분류**를 결합한다. 오행·계절·다른 출생 위치를 뒤섞어 성격·사건·기운 강약을 추정하지 않는다. 시주를 입력하지 않으면 시간 근거를 만들지 않는다.
- 모든 단계에 실제 sourceRefs와 제한 범위를 담는다. 같은 분류가 두 곳에 나오는 경우와 다른 분류가 나오는 경우의 판단 과제를 별도로 기록한다. 관계표의 일치는 실제 갈등이나 운의 변화로 해석하지 않는다.
- 검토된 DB 원고가 없는 사주도 **근거 계획은 작성할 수 있지만 보고서 본문은 계속 `not-covered`** 상태다. 해석 계획이 존재한다는 이유로 전자결제 후 노출 가능한 원고라고 판단하지 않는다.
- `report-core-knowledge-coverage.js`에서 99개 고정 사례의 **계산 성공 / 근거 계획 생성 / 검토용 원고 생성 / 계획의 차별성**을 따로 측정한다. 단순 근거 계획 보급률을 유료 품질 적용률로 표기하지 않는다.
- 이 코드 역시 개발용 별도 모듈이며 **운영·기존 API 요청·유료 생성 기능과 연결하지 않는다.**

### 향후 진짜 고급화의 필수 작업

1. 기본 의미의 명리학적 근거를 전문가가 검토한다. 10개 뜻을 저장하는 것만으로 고급 해석은 되지 않는다.
2. 근거 계획으로 찾아낸 구조적 차이가 어떤 **구체적인 해석 결론을 바꾸는지** 검증된 판단 규칙을 작성한다. 무의미한 지지 관계 목록을 보고서에 쌓지 않는다.
3. 누락된 분류 조합은 `not-covered`로 유지한 채, 사람의 승인 원고와 자동회귀를 함께 확보한다.
4. 해석문 문장 길이와 예시의 과잉 일반화·중복·출처 범위를 검토한다. API 과금 없이 오프라인으로 진행 가능해야 한다.
